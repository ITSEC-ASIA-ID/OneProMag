## 1. Summary

The NEW9220's shipped browser carries a Chromium **M80** vendor fork whose V8 is
vulnerable to the public 2020 n-day **CVE-2020-16040**. A single web page driven through the
browser's renderer obtains, with no user interaction beyond navigation:

1. **V8 memory corruption** — `Array(arrLen=-1)` Simplified-Lowering truncation, reproduced
   on every run (`E-025`, 14 Nov sweep);
2. **Arbitrary read/write of renderer memory** — `addrof` + typed-array backing-store
   redirect primitives;
3. **Arbitrary native ARM32 code execution** — wasm jump-table literal redirect: planted
   shellcode words execute inside the renderer process and return live values through
   HTTP beacons (`r=1337beef` control; `getpid=getuid` identity probes; **futex syscall
   probes**, §3). Payload runs end-to-end in ~1 s (`poc51_dx_*`, 14 Nov 10:00–10:01).

This is the first full code-execution primitive proven on this engagement not requiring
the plant (`su`) or any privileged context: the attacker's only input is a URL.

## 3. Post-mortem methodology (reusable): pulling the faulting PC out of a renderer crash

Two probes crashed (planted wasm-region words later walked by Blink as object pointers —
`strb r1,[r0,#0]` at `si_addr=0xd` via `r5=<planted lit>`; *not* the futex syscall, which
was alive and parked at dump time). The engagement now has a working, reproducible
crash-forensics channel:

- `core_pattern` in **file mode** under `/data/corefile` (label `coredump_file`, every
  domain may create/append; **pipe mode `|` is dead on this kernel** — kernel logs
  `Core dump to |… pipe failed` for every consumer, including a freestanding one);
  renderer cores are ~640 MB — check `df /data` (a 0-byte core means disk exhaustion);
- pull (≈18 s), parse NT_PRSTATUS (`pr_pid` @+24, `pc` @+132) + NT_SIGINFO
  (`si_addr` @ desc+12), select the faulting thread by mapped-PC, resolve against
  `libchrome.so`;
- full procedure: `E-053`.

**Secondary observation (policy-confirmed, cross-app access untested):** the SELinux policy
grants *every* domain `{ open read … unlink write }` on `coredump_file`, and `/data/corefile`
holds full process cores of crashed renderers/apps. If an untrusted app can read another
app's core there, that is a cross-process memory-disclosure surface on any crash. Worth a
5-minute device test on the next lab window (drop a canary string in a crashing app's
memory, read its core from a second app uid).

## 5. Final capability statement (matches E-050 §5)

A malicious URL yields attacker-controlled **native execution inside SprdBrowser's
renderer**: full memory R/W of the renderer, arbitrary syscalls within the sandbox
profile, and reliable HTTP beaconing. That is the terminal capability of the web chain on
this build; an OS shell or the payment stack is **not** reachable from it with measured
techniques. The step to full compromise is exactly one browser-process (or
one policy) bug — see F-007's pricing — which is the client's remediation priority.

## 6. Remediation

1. **Patch the engine**: the vendor fork pins Chromium M80 (2020). Updating SprdBrowser to
   a current Chromium (or replacing it) removes CVE-2020-16040 and the entire 2020-era n-day
   class (note the same engine also carries the libwebp 1.3.1 pre-1.3.2 code — F-004/E-042
   — i.e. two public renderer-memory bug families are simultaneously live in one process).
2. Interim: restrict what users can navigate to in the shipped browser (URL allowlist at
   the POS app/controller level) — the delivery channel is user navigation.
3. Fix the two structural amplifier bugs so that any *future* renderer bug stays
   renderer-local: add `allow_isolated` governance (remove what isn't needed; today zero —
   keep it that way) and keep denying `entrypoint` (correct today, verify on upgrades).
4. Verify `/data/corefile` cross-app readability (§3) and, if readable, move cores to a
   `0700`-owned directory or clear the `coredump_file` read grant for untrusted domains.

## 7. Relation to F-003

F-003 reported `adb root` as available and blamed a `userdebug` build. This finding
supersedes the mechanism: it is not that `adb root` *works on request*, it is that
`adbd` is **already root and already unauthenticated**, so the settings password
`170845` is not even needed to reach root. F-003's password recovery remains valid
and independent (it is reachable at the UI layer without ADB).

## 7. Exploitation demo addendum (E-047, 2026-11-14)

The root access described above was exercised end-to-end as a **network reverse
shell**: the terminal initiated a TCP connection to the operator host
(192.168.1.37:4444) and served `uid=0 ... context=u:r:su:s0` over it
(FIFO-wired toybox `nc` ⇄ `/system/bin/sh`; toybox `nc` has no `-e`). Commands
driven both from the host listener and from files piped into the device FIFO
executed as root. Full transcript: `tmp/m3/revshell_evidence.log`; write-up and
threat-model notes: `evidence/E-047_root_revshell_and_ghostlock_write_lane_verdict.md`
(Part 1). This demonstrates that the F-005 root surface is not merely a local
shell grant — the root shell can be relayed off-device over the terminal's own
network connection.
